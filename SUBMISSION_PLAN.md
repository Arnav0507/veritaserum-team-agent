# Two-hour submission plan

## Submission gates, in priority order

1. A successful real Meta model run, captured on video. The reference fixture alone does not demonstrate Stage One eligibility.
2. A working three-minute video showing useful joint work, not primarily blocked requests.
3. A public GitHub repository with reproducible setup and tests; no keys, database, sessions, or real private evidence.
4. Submission form completed and links tested with time remaining. Confirm the exact track/problem statement against the hackathon form; do not guess the category from an incomplete excerpt.

## Time allocation from the two-hour checkpoint

- Minutes 0–25: configure Meta key; run Spark private workers and Wonder coordinator on fresh prose evidence; fix integration errors before adding features.
- Minutes 25–45: rehearse the actual UI, verify candidate comparisons and final repair, capture evidence of model IDs and successful requests without secrets.
- Minutes 45–70: record the three-minute demonstration. Use synthetic data only. Capture real model/tool behavior; edit waiting time honestly.
- Minutes 70–90: edit narration/captions, upload the video, verify public/unlisted playback without account access.
- Minutes 90–110: complete repository README, CI result, submission text and links; test from a signed-out browser.
- Minutes 110–120: final submission buffer. Freeze features. Do not spend this buffer on another provider, model training, or a redesign.

## Rubric alignment

Impact (30%): first users are incident-response teams whose engineering, support and operations evidence cannot all be pooled. Demonstrate a concrete recovery that requires all three perspectives. Present time saved and leakage reduction as hypotheses, not measured production claims.

Meta tooling (25%): Spark turns private natural-language notes into reviewed disclosures. Wonder receives only approved claims and public knowledge, requests a simulator experiment, observes failed alternatives, and proposes a repair. The runtime mediates the information flow and authority. Meta runs the cognitive work; the model does not decide its own permissions.

Technical depth (20%): exact disclosure approval; authenticated participants; distinct private context construction; typed tool gateway; snapshot/revision checks; atomic and idempotent execution; revocation; durable provenance; reproducible tests.

Demo (25%): three identifiable participants, a visibly failing checkout, approved facts combining in the shared trail, competing repairs with actual test outcomes, then verified recovery. Keep one short boundary demonstration. The successful joint outcome is the climax.

## Three-minute storyboard and narration

**0:00–0:20 — The problem.** Show the degraded checkout and three seats.
“An incident spans support, engineering, and operations. Each person has evidence the others cannot see. Giving one agent every credential solves collaboration by giving up the boundaries. We built a shared agent that works through them.”

**0:20–1:00 — Three private perspectives.** Show Maya's synthetic customer escalation, Eli's diagnostic note, and Noor's migration constraint. Invoke their private workers; show natural-language notes and exact proposed claims. Each person approves their own disclosure. Keep private source panels visibly distinct from shared statements.
“Muse Spark works inside each person's context. It proposes the smallest fact our incident workflow needs. The owner sees the exact statement and decides whether it crosses into the team room.”

**1:00–1:35 — Shared reasoning with real tools.** Show the shared model ID, approved claims, and sandbox comparison.
“Muse Wonder sees the company runbook and those approved facts. It requests a real sandbox comparison: restart leaves the bug, rollback breaks schema compatibility, and disabling the feature passes. These are executed checks, not generated success claims.”

**1:35–2:10 — Authorized joint result.** Noor approves execution. Show the EU-wallet check change from FAIL to PASS and all regression checks passing.
“The model proposes; the runtime checks authority and evidence versions. Operations approves this exact repair. It commits only after verification. The team restored checkout without sharing the original customer, engineering, or deployment notes.”

**2:10–2:35 — One boundary check.** On a separate fresh pending plan, withdraw a dependency and show that the plan becomes stale. If this needs a separate take, make the transition explicit. Alternatively show an observer cannot execute the repair.
“Approval is bound to the evidence used. When that evidence changes, an old plan cannot act on stale authority.”

**2:35–3:00 — Architecture and credibility.** Show the decision trail and test command/CI. End on the verified result.
“One shared agent, private workers, explicit disclosure, and a checked execution boundary. The prototype has reproducible security and concurrency tests. The next step is real company connectors and incident-team pilots. The result is useful joint work despite the boundaries.”

## Recording requirements

Show the live model banner; do not label reference footage as Muse behavior. Never record the API-key prompt or environment variables. Use separate profiles for simultaneous collaborators; if switching seats in one browser, describe the demo as three authenticated roles, not three people concurrently typing. Record at a legible desktop width. Target 2:50–2:55 so encoding/title cards cannot exceed three minutes. Keep the original capture as evidence. Do not claim production deployment or zero-information leakage.

## Repository release contents

Include implementation, tests, CI, README, architecture, validation, and this script. Exclude local databases, credentials, sessions, captures containing secrets, and unrelated pre-hackathon research. No external deployment is required to make the source reproducible. Public source does not imply exclusive rights to the underlying idea.
